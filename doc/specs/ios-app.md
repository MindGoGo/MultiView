## 1. 背景與目標

使用者想在 iPad 上使用 MultiView：把畫面切成多格，同時看好幾場直播與影片，集中控制聲音。桌面版是 Electron，iOS 不能跑 Electron，也不能另外執行 yt-dlp 這類程式，所以 iOS 版用 SwiftUI 重新寫一個原生 App，功能和操作盡量跟桌面版一致，把滑鼠、視窗相關的部分改成觸控與 iPad 的多工方式。

使用者沒有 Mac，App 在 GitHub Actions 的 macOS 機器上編譯成沒有簽章的 IPA，再用 SideStore 以使用者自己的 Apple ID 簽章、安裝到 iPad。App 不上架 App Store，因此可以內附 yt-dlp 並讓它自動更新。

開發分成三個階段：

1. **技術驗證（R120–R122）**：先確認風險最大的三件事做得到，結果寫回本規格，必要時調整後面的需求。
2. **核心功能（R123–R134）**：多格播放、聲音、操作、保存。
3. **進階功能（R135–R144）**：yt-dlp、網頁來源、廣告阻擋、YouTube 小視窗、清單與訂閱、設定、匯入桌面版的資料。

- Mac 版（Mac Catalyst）
- 有 DRM 保護的串流（和桌面版相同）
- 桌面版專屬的功能：無邊框視窗、置頂、最小化（R1、R84、R85）、Windows 安裝檔（R11、R44）

## 3. 共用定義

沿用桌面版的定義：**格位（slot）**、**格子編號**、**顯示中的來源**、**隱藏的來源**（[multiview-player](multiview-player.md) 第 3 節），以及 **YouTube 播放器格子**、**yt-dlp 播放**、**解析**（[ytdlp-playback](ytdlp-playback.md) 第 3 節）。另外：

- **原生播放器：** iOS 內建的 AVPlayer，用來播 mp4、m3u8 和 yt-dlp 解析出來的串流。對應桌面版的「程式自己的播放器」。
- **網頁格子：** 用 WKWebView 顯示的格子，包括 YouTube 內嵌播放器、YouTube 網頁播放、整頁模式和一般網頁來源。
- **操作列：** 每一格下方的按鈕列，對應桌面版 R3 的「每一格的操作按鈕」。
- **工具列：** 畫面上方的全域按鈕列，對應桌面版 R3、R97 的「全域工具列」。
- **點一下：** 手指點一下後放開，沒有移動超過 10pt，按住不到 0.5 秒。
- **長按：** 按住 0.5 秒以上。
- **大螢幕：** App 畫面寬度和高度都至少 600pt，例如 iPad 全螢幕、iPad 分割畫面的一半（橫向）。其他情況是**小螢幕**，例如 iPhone、iPad 分割畫面的 1/3。
- **App 資料夾：** App 的 `Application Support/MultiView/`，對應桌面版的 `%APPDATA%\MultiView\`。

## 4. 需求清單

### 第一階段：建置與技術驗證

### R119：建置與安裝流程
- 描述：
  - iOS 版的程式放在 `ios/`。Xcode 專案由 XcodeGen 依 `ios/project.yml` 產生，repo 裡不放 `.xcodeproj`，避免沒有 Mac 時無法編輯專案檔。
  - 和畫面無關的邏輯（網址判斷、版型、格位、設定與清單的讀寫、yt-dlp 結果的判讀……）放在 Swift Package `ios/MultiViewCore/`，有自己的單元測試。
  - GitHub Actions（`.github/workflows/ios.yml`）在 macOS 機器上執行：
    - 推送到任何分支、而且有改到 `ios/` 時：跑 MultiViewCore 的單元測試，並在 iPad 模擬器上編譯一次。
    - 推送 `ios-v*` 標籤時（例如 `ios-v0.1.0`）：產生沒有簽章的 `MultiView-iOS-<版本號>.ipa`，上傳到 GitHub Releases 的同名版本。
    - 標籤由使用者建立（每次發佈都經過使用者）：在 GitHub 網頁的 Releases 建立新標籤並發佈，這時 Release 已經存在，Actions 只補上標題、說明和 IPA。
  - SideStore 用的「來源」檔 `sidestore-source.json` 列出最新版本的版本號、IPA 下載網址、更新內容。發佈新版時由 Actions 執行 `ios/scripts/make-source.py` 產生，上傳到固定的 GitHub Release `ios-source`（每次覆蓋），所以來源網址永遠是 `https://github.com/MindGoGo/MultiView/releases/download/ios-source/sidestore-source.json`。不放在 repo 的分支裡，避免 Actions 還要回頭推 commit。
  - 更新內容寫在 `ios/release-notes.txt`，用在 GitHub Releases 的說明和 SideStore 顯示的更新內容。
  - 標籤的版本號必須和 `ios/project.yml` 的版本號相同，不同時發佈失敗。
  - iOS 版的 Release 不標成 GitHub 的「最新版本」，README 的桌面版下載不受影響。
  - 來源檔和 IPA 要讓 SideStore 下載得到，repo 必須是公開的。
  - 在 SideStore 加入這個來源後，有新版時 SideStore 會提示更新；更新時保留 App 的資料（設定、清單、登入狀態）。
  - 安裝與更新步驟寫在 `doc/features/ios-app.md`，包括第一次在 Windows 電腦上準備 SideStore 的方式。
- 驗收條件：
  - AC1：推送一個改到 `ios/` 的 commit → Actions 跑完單元測試與模擬器編譯，結果是成功。
  - AC2：推送 `ios-v0.1.0` 標籤 → GitHub Releases 出現 `MultiView-iOS-0.1.0.ipa`，`ios-source` 版本裡的 `sidestore-source.json` 指向這個檔案。
  - AC3：在 iPad 的 SideStore 加入來源網址 → 看得到 MultiView，按安裝後可以開啟。
  - AC4：發佈 `ios-v0.1.1` 後 → SideStore 顯示有更新；更新後原本的格子、清單都還在。
  - AC5：IPA 沒有任何 App 延伸功能（解開 IPA，`PlugIns/` 資料夾不存在或是空的）。

### R120：技術驗證：多格原生播放
- 描述：
  - 做一個驗證用的畫面（只在開發版出現），用原生播放器同時播放 4 格與 9 格，確認：
    1. 4 格可以同時播放，而且可以同時出聲（AVAudioSession 用 `playback` 類別，不和其他 App 混音）。
    2. 每格可以各自靜音、各自調整音量 0%–100%。
    3. 在 iPad 上同時播放幾格 1080p、幾格 720p 不會掉格、不會過熱降速。
  - 結果寫在本規格第 11 節：使用者的 iPad 型號、iPadOS 版本、每種組合的結果。
  - 依結果決定 `3×3` 版型的預設畫質上限（R131）。
- 驗收條件：
  - AC1：4 格 m3u8 直播同時播放 10 分鐘，4 格都有聲音、都不中斷。
  - AC2：其中 1 格音量調到 30%、1 格靜音 → 只有這兩格的聲音改變。
  - AC3：第 11 節記錄了 4 格、9 格的畫質組合與結果。

### R121：技術驗證：多格網頁播放
- 描述：
  - 用 WKWebView 同時放 4 格 YouTube 內嵌播放器（不經過 YouTube 網站，由 App 自己提供載入播放器的頁面），確認：
    1. 可以在格子裡播放，不會自動跳成 iOS 的全螢幕播放器（`allowsInlineMediaPlayback`）。
    2. 不需要使用者先點一下就能開始播放（`mediaTypesRequiringUserActionForPlayback` 設為不需要）。
    3. 多格能不能同時出聲。
    4. 每格能不能各自調整音量。iOS 上網頁不能設定影片的音量，只能靜音或不靜音，所以要試用網頁的 Web Audio 加一道音量控制。
    5. YouTube 內嵌播放器的 API（播放、暫停、跳到某個時間、取得進度、畫質、字幕）都能用。
  - 也用一般影片網站（例如新聞台官網）測一次 3、4 項。
  - 結果寫在第 11 節。依結果調整 R128：
    - 多格不能同時出聲 → 網頁格子同一時間只有一格有聲音（點喇叭時其他網頁格子自動靜音，原生播放器的格子不受影響），並在 R128 寫明。
    - 不能各自調整音量 → 網頁格子的音量滑桿換成只有靜音／不靜音。
- 驗收條件：
  - AC1：4 格 YouTube 內嵌播放器在格子裡同時播放，沒有跳成全螢幕。
  - AC2：第 11 節記錄了同時出聲、各自音量的結果，以及 R128 要怎麼改。

### R122：技術驗證：內嵌 Python 與 yt-dlp
- 描述：
  - App 內附 iOS 版的 Python（Python 3.13 起官方支援 iOS，使用 BeeWare 的 `Python-Apple-support` 打包好的版本），在 App 裡面執行 yt-dlp。iOS 不能另外執行程式，所以 yt-dlp 是在 App 自己的程序裡、用另外的執行緒跑，不是像桌面版那樣執行 `yt-dlp.exe`。
  - yt-dlp 現在解析 YouTube 需要 JS 執行環境（桌面版用 Node 模式的 Electron）。iOS 上沒有 Node，改用 iOS 內建的 JavaScriptCore：寫一個 yt-dlp 的 JS 執行環境外掛，把要執行的 JS 交給 App，由 JavaScriptCore 執行後回傳結果。
  - 確認：
    1. 可以解析 YouTube 直播，得到 m3u8 串流，並用原生播放器播放。
    2. 可以解析 YouTube 一般影片，得到原生播放器能播的格式。原生播放器不能播 DASH，所以要用 HLS 格式或影音合在一起的格式。記錄最高能拿到的畫質。
    3. 可以解析一般影片網站（桌面版 R103），播放時能帶上需要的標頭（桌面版 R110）。
    4. 解析一次要多久；同時解析 4 格時，畫面會不會卡。
    5. 下載新版 yt-dlp（官方的 `yt-dlp` 檔案是 zip 格式的 Python 程式），放到 App 資料夾後可以直接改用新版，不需要重新安裝 App。
    6. App 多大。
  - 結果寫在第 11 節。如果第 2 項只能拿到 360p，在 R135 註明，並把「YouTube 一般影片播放方式」的預設值改成內嵌播放器。
- 驗收條件：
  - AC1：貼上 YouTube 直播網址 → 用 yt-dlp 解析，原生播放器開始播放。
  - AC2：把內附的 yt-dlp 換成下載的新版 → 重開 App 後，設定畫面顯示新版的版本號，可以正常解析。
  - AC3：第 11 節記錄了第 2、4、6 項的結果。

### 第二階段：核心功能

### R123：主畫面與裝置
- 描述：
  - 支援 iPadOS／iOS 17 以上的 iPad 和 iPhone。
  - 畫面只有影片格子，隱藏狀態列，iPad 也隱藏「Home 指示條」（手指往上滑時才出現）。
  - 可以橫向、直向使用。轉向或改變 App 大小時，版型和比例不變，影片不重新載入。
  - 工具列的旋轉按鈕：轉成另一個方向並固定（使用者關了 iOS 的自動旋轉也可以轉），再按一次轉回來；長按選「跟著裝置旋轉」解除固定。固定時按鈕顯示為啟用狀態。
  - iPad 支援分割畫面、Slide Over、幕前調度。App 從大螢幕變成小螢幕時，依 R124 改用小螢幕的版型。
  - 播放中不會自動鎖定螢幕；全部暫停超過 5 分鐘後恢復系統的自動鎖定。
- 驗收條件：
  - AC1：開啟 App → 只看得到格子和分隔線，看不到狀態列。
  - AC2：`2×2` 四格都在播放時把 iPad 轉成直向 → 版型維持 `2×2`，四格都繼續播放。
  - AC3：播放中 10 分鐘不碰螢幕 → 螢幕不會變暗或鎖定。
  - AC4：iPad 切成分割畫面，MultiView 占 1/3 → 改用小螢幕版型（R124 AC3）；拉回全螢幕 → 回到原本的版型。

### R124：版型
- 描述：
  - 大螢幕：和桌面版 R4 相同的 5 種版型 `1`、`2`、`2×2`、`3×3`、`1+3`。工具列的版型按鈕是依實際格子位置畫的圖示（`2` 版型上下排列時圖示也畫成上下）。
  - 小螢幕：只有 `1`、`2` 兩種。`2` 在畫面比較寬時左右排列，比較高時上下排列。
  - 小螢幕時，設定的版型如果是 `2×2`、`3×3`、`1+3`，暫時用 `2` 顯示（顯示第 1、2 格），其他格暫停，回到大螢幕時恢復原本的版型。這種暫時的切換不保存、不改變設定的版型，也不顯示「有 N 個來源暫時隱藏」的提示。
  - 小螢幕時在工具列選了 `1` 或 `2`，設定的版型就改成選的版型。
  - 其他規則和桌面版 R4 相同（隱藏的來源、預設版型 `2×2`）。
- 驗收條件：
  - AC1：iPad 全螢幕 → 工具列有 5 種版型可以選。
  - AC2：iPhone 直向，版型 `2` → 兩格上下排列；轉成橫向 → 左右排列，不重新載入。
  - AC3：iPad 上設成 `2×2` 四格都在播放，切成分割畫面的 1/3 → 顯示第 1、2 格，第 3、4 格暫停；拉回全螢幕 → 回到 `2×2`，第 3、4 格維持暫停。
  - AC4：AC3 的狀態下關閉 App 再開啟（全螢幕）→ 版型是 `2×2`。

### R125：分隔線與換位
- 描述：

### R128：聲音控制
- 描述：
  - 和桌面版 R7 相同：點一下有影片的格子 → 只有這一格有聲音（獨占聲音）；按喇叭按鈕（操作列上的，或工具列顯示時每一格左上角的，R127）→ 只切換這一格（多格聲音）；每格音量 0%–100%；有聲音的格子左上角顯示小喇叭。
  - **網頁播放的格子同一時間只有一格有聲音**（R121 實測，2026-11-13）：iOS 不讓兩個網頁同時出聲，第二個網頁出聲時系統會把第一個暫停。所以 YouTube 內嵌播放器和網頁來源的格子，按喇叭取消靜音時，其他這類格子自動靜音，並提示「YouTube 和網頁的格子同一時間只能有一格有聲音」。原生播放器的格子（mp4、m3u8、之後的 yt-dlp 播放）不受影響，可以和其他格子同時出聲。
  - 切換聲音時被系統暫停的網頁播放格子（已經靜音的），約 1 秒後自動繼續播放。
  - YouTube 內嵌播放器和網頁來源沒有音量滑桿，只有靜音開關（iOS 上網頁不能設定影片的音量）。
  - 音量用按鈕＋彈出滑桿（桌面版 R42），最高 100%，不做 R98 的 200%。
  - 系統音量鍵調整的是整台裝置的音量，不改變每格的音量。
  - 其他 App 開始播放聲音（例如來電、別的影片 App）時，MultiView 全部暫停；中斷結束後，系統表示可以恢復時，恢復中斷前正在播放的格子。
  - 拔掉耳機時全部暫停（iOS 的慣例）。
- 驗收條件：
  - AC1：第 1、2 格都有聲音，點一下第 3 格 → 只有第 3 格有聲音。
  - AC2：兩格都是 m3u8，只有第 1 格有聲音，叫出工具列後按第 2 格左上角的喇叭 → 第 1、2 格都有聲音。
  - AC5：兩格都是 YouTube 內嵌，只有第 1 格有聲音，按第 2 格左上角的喇叭 → 只有第 2 格有聲音，出現提示；第 1 格約 1 秒後繼續播放（沒有聲音）。
  - AC3：播放中有來電，掛斷後 → 原本在播的格子恢復播放。
  - AC4：戴藍牙耳機播放中，把耳機收回盒子 → 全部暫停。

### R131：畫質、字幕、進度條的預覽縮圖
- 描述：
  - **畫質**：原生播放器播 HLS（m3u8 網址、YouTube 與其他網站用 yt-dlp 播放）時，操作列有畫質選單（寬的操作列是電視圖示，窄的在「⋯」裡），選項是自動、1080p、720p、480p、360p，目前的選項打勾。選了之後用 iOS 的 `preferredMaximumResolution` 限制最高畫質，系統只在不超過的畫質之間自動切換；選「自動」時由系統依網路決定。畫質跟著來源保存（和桌面版 R24 相同）。
  - mp4 只有一種畫質、內嵌播放器與網頁格子 iOS 不能指定畫質，這些格子沒有畫質選單。
  - 依 R120 的結果（iPad Pro M1 的 `3×3` 不會卡頓，2026-11-14 使用者實測），格子多時不另外限制畫質。
  - **字幕**（桌面版 R31；0.0.30，從 Android 版 0.0.16 補回，待實測）：只有 yt-dlp 播放（YouTube、其他網站）有，內嵌播放器與網頁格子沒有字幕選單。
    - `mv_bridge.py` 的 `resolve` 回傳 `info.captions`：`[{"lang", "name", "url", "auto"}]`（人工字幕，加上自動產生的原本語言，也就是 yt-dlp 的 `語言-orig`；自動翻譯的不列；只取 WebVTT）。`MultiViewCore` 的 `CaptionRules.fromYtDlp` 轉成字幕清單，放在 `YtStream.captions`：key 是語言代碼，自動產生的前面加 `asr:`（和桌面版 R31 的設定檔格式相同）；標籤是繁體中文的語言名稱，自動產生的加「（自動產生）」；重複的只留第一個。
    - 有字幕時操作列有「字幕」（CC 圖示，開著時用強調色；窄的操作列在「⋯」裡）。選單是「關閉」和各軌，目前的打勾。選了之後提示「字幕：<名稱>」，存進來源的 `captions` 並保存。
    - 原生播放器自己下載字幕檔（帶 yt-dlp 給的 User-Agent、Referer）並用 `CaptionRules.parseVtt` 解析：去掉 `<…>` 標籤（YouTube 自動字幕每個字的時間）、YouTube 自動字幕捲動重複的那一行不重複顯示、略過 0.05 秒以下的過渡段。用 `addPeriodicTimeObserver` 約每 0.2 秒依播放位置（`CaptionRules.cueAt`）更新疊在影片下方的文字：白字、半透明黑底，字的大小是格子高度的 5%（最小 10pt），寬度最多是格子的 90%。讀不到字幕不影響播放。
    - 建立播放器時依來源的 `captions` 用 `CaptionRules.find` 自動開啟：先找完全相同的，再找同一種語言的（優先人工字幕）；都沒有就關閉。更換網址時沿用原本的選擇（和桌面版相同），新的影片依同樣的規則找。外層的 `YouTubeSourcePlayer`、`WebSourcePlayer` 把選擇轉給裡面的原生播放器並記住，重新解析時沿用。
  - **進度條的預覽縮圖**（桌面版 R50；0.0.30，從 Android 版 0.0.16 補回，待實測）：拖曳進度條時，手指上方顯示那個位置的時間（可回放的直播顯示距離最新位置多久）。
    - YouTube（yt-dlp 或內嵌）、mp4 的一般影片，時間上方多一張 160pt 寬的縮圖：
      - YouTube：用桌面版的 User-Agent 下載 `https://www.youtube.com/watch?v=<id>`，取出 `playerStoryboardSpecRenderer`（`MultiViewCore` 的 `StoryboardRules`，照搬 `src/lib/storyboard.ts`：選寬度不超過 320 的最大等級），下載那一頁圖片後裁切。每部影片的縮圖資訊、整頁圖片、裁切好的縮圖都快取；網路錯誤時不記住，下次再試。
      - mp4：`AVAssetImageGenerator` 取那個位置附近（前後 1 秒內）的畫面，每 2 秒一張並快取。
    - m3u8、其他網站只顯示時間；進度條比縮圖窄時只顯示時間。提示不超出進度條的左右範圍。
    - 程式在 `Cell/ControlsBar.swift`（`ProgressPreview`）、`Players/PreviewThumbnails.swift`。
- 驗收條件：
  - AC1：m3u8 直播格子選 480p → 畫面變成 480p 左右；選「自動」→ 恢復由系統決定。
  - AC2：yt-dlp 播放的 YouTube 格子有畫質選單；內嵌播放器的格子沒有。
  - AC3：選 720p 後關閉 App 再開啟 → 那一格仍然是 720p。
  - AC4：yt-dlp 播放有字幕的 YouTube 影片（TED `iG9CE55wbtY`），選中文字幕 → 幾秒內影片下方出現中文字幕，跟著影片的時間換；關閉 App 再開啟 → 字幕仍然開著。沒有字幕的影片（`aqz-KE-bpKQ`）沒有「字幕」。
  - AC5：拖曳 YouTube 一般影片的進度條 → 手指上方出現縮圖和時間；m3u8 只有時間；拖到最左、最右時提示不超出進度條。

### R132：背景播放、子母畫面、AirPlay
- 描述：
  - 回到主畫面或鎖定螢幕時：原生播放器中「有聲音而且正在播放」的格子繼續播放聲音；其他格子暫停。回到 App 時，因為切到背景而暫停的格子恢復播放。
  - 鎖定螢幕時系統不會啟動子母畫面，影片會先被系統暫停：App 在約 1 秒內改成只播聲音並繼續播放。
  - 在畫面邊緣拖曳時（下方格子的操作列、進度條），第一次滑動不會直接回到主畫面或拉出控制中心（系統手勢延後）。
  - 網頁格子在背景時一律暫停（iOS 會暫停背景的網頁）。
  - 鎖定畫面和控制中心顯示正在播放的那一格（只有一格有聲音時）的名稱，可以播放／暫停。
  - 子母畫面：操作列的選單有「子母畫面」（只有原生播放器的格子有）。另外，回到主畫面時，如果只有一格有聲音而且是原生播放器在播放，自動用子母畫面繼續播這一格。
  - AirPlay：工具列有 AirPlay 按鈕，可以把聲音送到 AirPlay 喇叭或 Apple TV（只送聲音，畫面留在 iPad）。
- 驗收條件：
  - AC1：m3u8 直播格子有聲音，回到主畫面 → 影片在子母畫面繼續播；回到 App → 子母畫面關閉，所有格子恢復播放。
  - AC2：只有 YouTube 內嵌格子有聲音，回到主畫面 → 全部暫停；回到 App → 恢復播放。
  - AC3：鎖定螢幕 → 鎖定畫面顯示正在播放的影片名稱，按暫停後 App 裡的格子也暫停。

### R133：接實體鍵盤時的快捷鍵

### R136：yt-dlp 更新
- 描述：
  - App 內附打包當時的 yt-dlp（放在 App 裡的 `site-packages`，不能修改）。更新時下載的新版放在 App 資料夾的 `bin/yt-dlp.zip`；有這個檔案時 Python 優先載入它，沒有時用內附的（對應桌面版 R91）。
  - App 的版本換了的時候（和 `bin/update.json` 記錄的不同），內附的 yt-dlp 可能比較新，所以刪掉下載的那一份，並把上次檢查的時間歸零，之後照常重新檢查更新。
  - 更新方式：向 GitHub 查詢 yt-dlp 最新穩定版的版本號，比目前使用的新才下載。下載官方的 `yt-dlp` 檔案（zip 格式的 Python 程式）和 `SHA2-256SUMS`，驗證雜湊值後存成 `bin/yt-dlp.zip`。查詢、下載或驗證失敗時保留原本的，播放不受影響。
  - **新版在下次開啟 App 時生效**：已經載入的 yt-dlp 不能在執行中換掉。下載完成後，齒輪選單顯示「重新開啟 App 後使用 <版本>」。
  - 自動更新的時機：
    1. 開啟 App 約 5 秒後，距離上次檢查超過 24 小時 → 在背景檢查，不顯示任何訊息；24 小時內再開啟不重複。
    2. 解析失敗，而且錯誤看起來是 yt-dlp 太舊 → 這一格依 R135 退回內嵌播放器，同時在背景更新；有下載到新版時提示「yt-dlp 已下載 <版本>，重新開啟 App 後生效」。10 分鐘內只因為這個原因更新一次。和桌面版 R92 不同：不能更新完馬上重新解析。
  - 同一時間只進行一個更新；自動和手動同時發生時共用同一次的結果。
  - 自動更新遇到低數據模式時不下載；手動更新不受限制。
  - 新版 yt-dlp 需要的 JS 解題程式和 App 內附的版本不同時，允許 yt-dlp 從它自己的 GitHub 下載對應的版本（yt-dlp 會檢查雜湊值）。
  - 下載的新版載入失敗時（檔案損毀）：自動改用內附的版本，刪掉下載的檔案，之後重新下載。
  - 齒輪選單顯示目前使用的 yt-dlp 版本，以及「檢查 yt-dlp 更新」；手動檢查完成後提示「yt-dlp 已下載 <版本>，重新開啟 App 後生效」「yt-dlp 已經是最新版」或「yt-dlp 更新失敗：<原因>」（對應桌面版 R93）。
  - 上次檢查的時間、上次開啟時的 App 版本記錄在 App 資料夾的 `bin/update.json`。
- 驗收條件：
  - AC1：有比內附更新的 yt-dlp 時，開啟 App 一會兒後打開齒輪選單 → 顯示「重新開啟 App 後使用 <新版>」；從 App 切換器滑掉再開啟 → 選單顯示新版的版本號，YouTube 照常用 yt-dlp 播放。
  - AC2：24 小時內再開啟 App → 不重複檢查。
  - AC3：按「檢查 yt-dlp 更新」→ 顯示三種提示之一。
  - AC4：開啟低數據模式 → 不自動更新；按「檢查 yt-dlp 更新」→ 照樣更新。
  - AC5：把 `bin/yt-dlp.zip` 換成壞掉的檔案（測試用）→ 開啟 App 後 YouTube 照常用內附的 yt-dlp 播放，壞掉的檔案被刪掉。

### R137：網頁來源與整頁模式
- 描述：
  - 一般網頁來源（桌面版 R12–R16）、YouTube 網站頁面（R57）、網頁找不到影片時自動按播放鈕（R113）、切到網頁時立即維持暫停（R75），規則和桌面版相同。
  - **注入網頁的程式直接重用桌面版的 `electron/webPreload.ts`**：編譯時由 `ios/scripts/build-web.sh` 用 esbuild 打包成一個檔案，`import { ipcRenderer } from 'electron'` 換成 `ios/web/electron-shim.ts`（訊息改走 WKScriptMessageHandler、App 用 `window.__multiViewReceive` 送狀態進去），用 WKUserScript 注入每一個框架。找主要影片、只顯示影片、回報播放狀態與進度、按網站的播放鈕的行為和桌面版一致，桌面版修改後 iOS 版跟著改。
  - Safari 17.4 以前沒有 `Element.checkVisibility`，shim 用樣式判斷補上。
  - **影片模式**（預設）：只顯示網頁中的主要影片，點擊由格子攔下（點一下切換聲音、叫出操作列）。網頁以比較寬的版面排版（桌面版 R13 是至少 1280×720），格子小時網站會改用手機版的窄版面，影片常常排在畫面外面而找不到。iOS 版用 WKWebView 的網頁縮放（pageZoom，最小 50%）做到，只畫格子實際大小的畫面；不能把網頁畫成很大一張再縮小，iPhone 的記憶體不夠。寬版面只在找影片的期間使用；找到影片後恢復成原本的大小，否則影片填滿的「畫面寬度」是縮放後的寬度，只會露出一半。網頁載入完成 3 秒後還找不到影片就按一次網站的播放鈕；15 秒還找不到就切換成整頁模式並提示「找不到影片，可以在網頁中操作後按「只顯示影片」」。
  - **整頁模式**：手指直接操作網頁，可以捲動、點連結、打字、從左緣右滑回上一頁；操作列用格子下緣的小把手叫出（R127）。
  - 操作列的「顯示整個網頁」「只顯示影片」切換顯示方式。切換廣告阻擋（R138）而重新載入時保留原本的顯示方式（和桌面版不同：桌面版回到影片模式；使用者回報在整頁模式切換時又開始找影片、一直顯示讀取中）。按「只顯示影片」時找得到影片就切換；找不到時先按一次網站的播放鈕，6 秒內找到就切換，否則提示「找不到影片」。顯示方式不保存，重新開啟時從影片模式開始。
  - YouTube 網站頁面（首頁、搜尋、頻道等）一律以整頁模式顯示；在網頁裡點影片時不換頁，這一格換成那部影片（依 R135 的播放方式）。回到原本的頁面（R63）之後再做。
  - 網頁要開新視窗一律擋下（和桌面版相同）。
  - 錯誤（桌面版 R16）：第一次載入 30 秒還沒開始顯示（「無法載入網頁（逾時）」）、主文件 HTTP 400 以上時顯示「無法載入網頁」；網頁程序被系統結束時自動重新載入一次，還是被結束才顯示「網頁停止運作」；影片需要 DRM 時顯示「這個影片有版權保護，無法播放」。網頁載入完成過之後，網站自己發起的跳轉失敗（例如導向 App 專用的連結）不算錯誤，原本的網頁照常顯示；顯示錯誤後網頁換成新的頁面、或網頁回報找到影片時，取消錯誤。網頁開始顯示（WebKit 的 didCommit）就算載入成功，不等「載入完成」：新聞網站常常一直在載入廣告、推薦內容，等不到載入完成（和桌面版不同）。
  - 影片模式還沒找到影片時，用黑色蓋住網頁（桌面版 R13），中間顯示讀取動畫。
  - 網頁格子的聲音同一時間只有一格（R128）。
  - **其他網站的播放方式**（桌面版 R102、R103）：設定畫面可以選「網頁」（預設）或「yt-dlp」。選 yt-dlp 時先用 yt-dlp 解析，成功就用原生播放器播放（可以多格同時出聲，顯示「yt-dlp」小標示，串流請求帶網頁網址當 Referer，R110）；不支援的網站或解析、播放失敗時顯示網頁。YouTube 網站頁面一律用網頁。
- 驗收條件：
  - AC1：貼上新聞台官網的直播頁 → 只顯示網頁中的影片，可以播放。
  - AC2：按「顯示整個網頁」→ 看得到完整的網頁，可以捲動、點連結、打字；按「只顯示影片」→ 回到只顯示影片。
  - AC3：在整頁模式點會開新視窗的連結 → 不開新視窗。
  - AC4：從整頁模式格子的左緣往右滑 → 回到上一頁。
  - AC5：貼上沒有影片的網頁 → 15 秒後自動切換成整頁模式並提示。
  - AC6：貼上 `https://www.youtube.com/` → 整頁顯示 YouTube 首頁；點一部影片 → 這一格開始播放那部影片。
  - AC7：設定的其他網站選 yt-dlp，貼上 yt-dlp 支援的網站（例如 Twitch 頻道）→ 顯示「yt-dlp」小標示並播放；貼上不支援的網站 → 顯示網頁。

### R138：廣告阻擋
- 描述：
  - 規則和桌面版 R17 相同：網頁格子預設開啟，每格各自切換（操作列的盾牌按鈕，切換後那一格重新載入），開關跟著來源保存；其他網站裡內嵌的 YouTube 播放器不阻擋。
  - 改用 WebKit 的內容阻擋規則（WKContentRuleList）。EasyList 在編譯時由 `ios/scripts/easylist-to-webkit.mjs` 轉成 WebKit 的規則格式，放進 App：
    - 轉換網路規則（`||網域^`、網址片段、`$third-party`、`$domain=`、請求類型）、例外規則（`@@`）、元素隱藏規則（`##`、`網域##`、`網域#@#`）。
    - WebKit 做不到的規則略過：正規表示式、`$csp`、`$redirect`、`$popup` 等選項、擴充的元素隱藏語法（`#?#` 等）、同時有套用與排除網域的規則、`google.*` 這類網域。2026-10-08 版的 EasyList 轉出約 5.1 萬條網路規則、5800 條隱藏規則，略過約 4300 條。
    - 分成 7 份清單（每份最多約 1 萬條網路規則，例外規則附在每一份後面）。一份編譯失敗時只略過那一份。
    - 只能擋網路請求和隱藏元素，不能像桌面版那樣依頁面上出現的元素動態隱藏。
  - 第一次開啟 App 時在背景編譯，之後沿用系統保存的結果；EasyList 版本換了才重新編譯。網頁格子開啟時最多等 2 秒，規則還沒準備好就先不擋，不重新載入。
  - 設定畫面顯示規則的狀態：「準備中…」，或「N／7 份可以用，約 M 條（EasyList 版本）」。
  - 「其他網站裡內嵌的 YouTube 播放器不阻擋」用 WebKit 的 `if-frame-url` 例外規則做到；如果系統不支援這個寫法，那一份清單改成不加這條例外再編譯一次。整個格子是 YouTube 網頁時（R57）目前也不阻擋。
- 驗收條件：
  - AC1：廣告阻擋開啟 → 測試頁請求 `https://pagead2.googlesyndication.com/pagead/js/adsbygoogle.js` 被擋下，一般網址的請求正常。
  - AC2：在其中一格關閉廣告阻擋 → 那一格重新載入，不再阻擋；其他格仍然阻擋。
  - AC3：開啟飛航模式後開啟 App → 廣告阻擋照樣啟用，不顯示錯誤。

### R161：SponsorBlock（跳過業配等片段，0.0.35）
- 背景：和 Android 版的 R161 是同一個需求、同一個編號（規則、範圍、類別、預設值、驗收條件都以 [android-app.md](android-app.md) 的 R161 為準），這一節只寫 iOS 版的做法與 iOS 特有的部分。資料來自 [SponsorBlock](https://sponsor.ajay.app)，授權 CC BY-NC-SA 4.0，README 的第三方元件與設定畫面註明來源。
- 範圍：只處理 yt-dlp 播放的 YouTube 一般影片（原生播放器）；內嵌播放器、網頁格子與整頁模式、直播、mp4／m3u8／其他網站不處理。不做的項目同 Android 版。
- 描述：
  - **規則**：`ios/MultiViewCore/Sources/MultiViewCore/SponsorBlock.swift`，照搬 `android/core/.../SponsorBlock.kt`（`SponsorCategory`、`SponsorSegment`、`SponsorBlockSettings`、`SkipState`、`SkipAction`、`SegmentMark`、`SponsorBlockRules`）；測試 `SponsorBlockTests.swift` 照搬 `SponsorBlockTest.kt` 的每一個案例。影片 ID 的 SHA-256 前 4 碼用 CryptoKit 的 `SHA256`。設定檔的 `sponsorBlock` 欄位在 `SettingsCodec` 讀寫，格式和 Android 版相同（`{"enabled": true, "categories": ["sponsor"]}`），沒有這個欄位時預設開啟、只跳過業配。
  - **請求**（`Players/SponsorBlockClient.swift`）：`URLSession`（`ephemeral`，連線到讀完全部最多 5 秒，User-Agent `MultiView`），隱私版 API `GET https://sponsor.ajay.app/api/skipSegments/<前 4 碼>?categories=[全部 8 類]`。200 解析、404 是沒有片段、其他狀態碼與錯誤、逾時都當作沒有片段，不影響播放。App 執行期間在記憶體快取（同一部影片好幾格共用同一個請求）；失敗的不留在快取裡，下次建立這部影片的播放器時再試。
  - **何時抓**（`Players/YouTubeSourcePlayer.swift`）：建立播放器時就在背景抓（開啟、一般影片的播放方式是 yt-dlp 時），和 yt-dlp 解析同時進行；解析出來是一般影片時把片段與設定交給 `NativePlayer`，是直播時取消、不處理。設定從關閉改成開啟時，還沒抓過的才去抓。
  - **跳過**（`Players/NativePlayer.swift`）：
    - 用 `addPeriodicTimeObserver` 每 0.25 秒依播放位置檢查（`SponsorBlockRules.check`，和字幕的 0.2 秒、狀態回報的 0.5 秒是各自的觀察器），進入還沒處理過的片段時用精準的 `seek(to:toleranceBefore: .zero, toleranceAfter: .zero)` 跳到片段結尾（結尾在影片最後 1 秒內時跳到影片長度，視為播完）。只在 `timeControlStatus` 不是暫停、而且不是直播時跳。
    - **另外在每個片段開頭（開始 + 0.05 秒）放一個 `addBoundaryTimeObserver`**，播放經過時也做同樣的檢查：背景只播聲音、子母畫面時定時觀察器如果沒有執行，也會在片段開頭跳過。兩個觀察器呼叫同一個檢查，跳過的片段標成處理過，不會重複跳。
    - 使用者自己跳轉（拖曳或點進度條、雙擊快轉倒轉、鍵盤快捷鍵，都經過 `seek(to:)`）時，落點所在的片段標成處理過（`SkipState.userSeeked`），不會馬上被跳走。自動跳過、取消不經過 `seek(to:)`。
    - 從上次的觀看進度開始（R55）：片段來了之後，上次的位置所在的片段當作使用者自己跳進去的，不跳。
    - 狀態每一格各自保存，只在記憶體；播放中斷後重新解析（R135）會建立新的原生播放器，跳過的狀態重新開始。
    - `shutdown()` 時移除定時與片段開頭的觀察器、取消提示的計時；`YouTubeSourcePlayer.shutdown()` 取消這一格等待中的請求（共用的請求不取消，其他格子可能在等，最多 5 秒）。
  - **跳過提示**（`Cell/SkipNoticeView.swift`，放在 `CellView` 的右上角）：「● 已跳過<類別名稱>　取消」，圓點是類別的顏色；工具列顯示而且格子在最上面一列時往下移，避開工具列。5 秒後收起（由 `NativePlayer` 計時，App 在背景時也照樣計時）。按「取消」跳回片段開頭，這個片段之後不再跳。
  - **進度條**（`Cell/ControlsBar.swift`）：一般影片的進度條上用類別的顏色畫出片段（`SponsorBlockRules.marks`，最窄 2pt），畫在已播放的部分上面。拖曳進度條時手指在片段上的話，預覽提示多一行「<顏色> <類別名稱>」。
  - **設定**（`Panels/SettingsView.swift` 的「SponsorBlock（跳過業配）」）：「自動跳過片段」開關（預設開啟）；開啟時列出 8 個類別的勾選（左邊是進度條的顏色，預設只勾「業配」）；說明與資料來源。改了馬上套用到每一格，不用重新載入；保存在設定檔，匯入桌面版設定時沒有這個欄位就用預設值。
  - **iOS 特有：背景播放與子母畫面**（R132）：
    - 回到主畫面或鎖定螢幕時只播聲音（`continueAudioOnly` 把畫面從播放器拿掉）、子母畫面繼續播放時，App 在背景（`UIBackgroundModes` 有 `audio`），AVPlayer 的觀察器排在主佇列上，照常執行，所以照樣跳過。這兩種情況都沒有辦法在開發環境驗證（沒有 iOS 裝置），以第 11 節的實測為準；如果實測發現定時觀察器在背景不執行，片段開頭的 `addBoundaryTimeObserver` 仍然會跳過（這是上面同時放兩種觀察器的原因）。
    - 背景跳過時看不到提示；回到 App 時如果還在 5 秒內會看到提示。
    - 鎖定畫面、控制中心的進度跟著跳過後的位置（狀態回報照常）。
- 驗收條件（AC1–AC10 同 Android 版 R161，下面是 iOS 版的寫法與多的項目）：
  - AC1：用 yt-dlp 播一部有業配標記的 YouTube 影片，播到業配開始時自動跳到業配結束，右上角顯示「已跳過業配　取消」，5 秒後消失。
  - AC2：按「取消」跳回業配開頭，整段業配播完不再被跳過；倒回去重看已經跳過的業配也不再跳。
  - AC3：拖曳進度條到業配中間，從那裡繼續播放，不會被跳走；拖到業配前面，播放進入業配時照樣跳過。
  - AC4：進度條上業配的位置有綠色色塊；拖曳進度條經過業配時，預覽提示顯示「業配」。
  - AC5：設定關閉 SponsorBlock 後，色塊消失、不再跳過；勾選「開場」等其他類別後，那些片段也有色塊、也會跳過；設定在重開 App 後保留。
  - AC6：鎖定螢幕（只播聲音）時，播到業配也會跳過；解鎖後位置在業配之後。
  - AC7：回到主畫面、在子母畫面播放時，播到業配也會跳過（子母畫面的畫面跳到業配之後）。
  - AC8：兩格各播一部（或同一部）有業配的影片，各自跳過、各自的提示與取消互不影響。
  - AC9：連不到 SponsorBlock 時，影片照常播放，沒有色塊、沒有錯誤訊息；內嵌播放器、網頁格子、直播沒有色塊、不跳過。
  - AC10：`ios/MultiViewCore` 的 `SponsorBlockTests` 全部通過（在 GitHub Actions 的 `swift test`）。

### R162：只有一格時的顯示、上下排的小視窗、在小視窗裡看影片（同 Android 版 R162，0.0.36）
- 背景：和 Android 版的 R162 是同一個需求、同一個編號（行為與驗收條件以 [android-app.md](android-app.md) 的 R162 為準），這一節只寫 iOS 版的做法與差異。使用者要求（2026-11-17）Android 版 0.0.21 做完後照搬。
- 描述：
  - **小喇叭**（`Cell/CellView.swift`）：工具列沒有顯示時常駐的「有聲音」小喇叭，在實際顯示的版型（`displayedLayout`）是 `1`、或單格全螢幕（`solo != nil`）時不顯示。工具列顯示時左上角的靜音按鈕不變。
  - **上下排**（`App/RootView.swift`）：
    - 條件：小視窗開著、整個畫面（包括安全區域）是直向而且是小螢幕（`ScreenRules.isLarge` 為 false，也就是 iPhone）、畫面上只有一格（版型 `1` 或單格全螢幕）。iOS 版沒有 Android 版的「子母畫面中」條件（iOS 的子母畫面在 App 外面）。
    - 格子區域縮成占滿寬度、16:9（`寬 × 9 / 16`），從安全區域上緣開始（動態島下面）；小視窗用 `padding(.top:)` 接在影片下面，占剩下的高度到安全區域下緣，不跟著工具列移動。一直是同一個 `GridView`，只改 `frame` 與 `padding`（沒有 `if` 分支），格子的畫面與播放器不會重新建立、不重新載入。上下排時傳給 `GridView` 的安全區域上下是 0（影片本身已經在安全區域裡）。
    - 上下排的狀態由畫面回報給 `AppModel.companionStacked`；這時工具列照常自動隱藏（`ToolbarView` 的 `holdControls` 不算小視窗）。
    - 轉成橫向時條件不成立，小視窗回到原本的位置（占滿寬度、蓋在影片上）。
  - **方向**（`App/AppModel.swift`、`App/Orientation.swift` 不變）：
    - `enterSolo`：小視窗開著時不轉成橫向（維持直向、上下排）。
    - `toggleCompanion`：iPhone 單格全螢幕、目前是橫向時打開小視窗：記下目前的方向固定（`Orientation.locked`，進入全螢幕時自動轉的是 `.landscape`、旋轉按鈕固定的方向、或 nil 跟著裝置），轉成 `.portrait`。
    - `hideCompanion`（關閉按鈕、打開清單、`listPanelOpen` 的 `didSet` 都經過這裡）：如果是上面轉成直向的、而且還在全螢幕，轉回 `.landscape`；原本是跟著裝置的，轉回橫向後再解除固定（和離開全螢幕時「先轉回直向再解除」的做法相同）。
    - `exitSolo`：進入全螢幕時自動轉過的（`rotatedForSolo`）照舊轉回直向再解除；否則如果打開小視窗時轉成了直向，回到記下的方向固定。旋轉按鈕、解除固定時清掉這個記號。
    - 和 Android 版的差異：iOS 版原本就是「方向被旋轉按鈕固定時，進入全螢幕不自動轉」（R129），這一點不變。
  - **在小視窗裡看**（`Panels/CompanionPanel.swift`）：
    - 搜尋分頁的標題列在關閉按鈕左邊多一個圖示按鈕：`square.grid.2x2`（放進格子，預設）／藍色的 `play.rectangle.fill`（在這裡看），按一下切換並顯示提示「點影片：放進格子」「點影片：在小視窗裡看」。選擇存在 `UserDefaults` 的 `companionBrowse`，不寫進和桌面版共用格式的設定檔。
    - 在這裡看時，注入的 JS 設 `window.__multiViewBrowse = true`，點擊不攔截，網頁照常換頁、播放（網頁重新載入時由 `ready` 訊息再設一次）。
    - 上方的標題與分頁 3 秒沒有按上面的按鈕、分頁就隱藏（`.task(id:)` 計時），留一條小把手，點一下叫出來。不是在這裡看時一直顯示。
    - 「上一頁」（`chevron.backward`）：WKWebView 的 `canGoBack` 為 true 時才顯示（用 KVO 觀察）。搜尋分頁原本就可以從左邊緣滑動回上一頁（`allowsBackForwardNavigationGestures`）。iOS 沒有返回鍵，所以 Android 版的 AC6 改成「上一頁」按鈕與滑動手勢。
    - 「放進格子」（`rectangle.stack.badge.plus`）：目前的網址（KVO 觀察 `url`，包括 YouTube 手機版不重新載入的換頁）是單一 YouTube 影片時才顯示；網頁裡的影片先暫停，放進空格，沒有空格時詢問要取代哪一格（`companionOpenVideo(replaceLinkedCell: false)`）。
    - 搜尋分頁的網頁交給 App 的物件是 `CompanionBrowser`（`AppModel.companionBrowser`）：目前的網址、能不能回上一頁、暫停網頁裡的影片（`document.querySelectorAll('video')` 全部 `pause()`）。
    - 推薦、留言、聊天室分頁不受影響（JS 的 `__multiViewBrowse` 只在搜尋分頁設定；那三個分頁一樣 `.all` 需要使用者操作才播放、一開始播放就暫停）。
  - **聲音**：
    - 注入的 JS 在 `window` 上用捕捉階段監聽 `playing` 與 `volumechange`（媒體事件不會冒泡，捕捉階段收得到）：在這裡看、影片沒有靜音、正在播放時送 `playing` 訊息。搜尋結果裡靜音的預覽不算；靜音開始播放、之後打開聲音也算。
    - 收到時正在播放的格子暫停，並記下來（`companionPaused`）。關掉小視窗、切到其他分頁、改回放進格子時，網頁的影片暫停，記下的格子恢復播放（App 在背景時不恢復），恢復前再設定一次 App 的 `AVAudioSession`（`.playback`／`.moviePlayback`、`setActive(true)`）。
    - 使用者按格子的播放時，網頁的影片暫停，記下的格子清空（只播按的那一格）。
    - 搜尋分頁的 `mediaTypesRequiringUserActionForPlayback` 從 `.all` 改成 `.audio`：有聲音的影片要使用者點過才播放，靜音的可以自動播放（YouTube 手機版換到影片頁後常常先靜音自動播放，使用者再點一下打開聲音；`.all` 時連靜音的都不會播）。放進格子模式下影片頁不會打開，只有搜尋結果的靜音預覽可能播放，不出聲。
  - **WKWebView 播放時對 `AVAudioSession` 與格子的影響**（開發環境不能驗證，以第 11 節的實測為準）：
    - WKWebView 的影片在 WebKit 自己的程序裡播放，但聲音算在 App 的 `AVAudioSession` 上。App 的類別是 `.playback`、不混音，WebKit 播放時不會打斷 App 自己的原生播放器（同一個 App 的多個 AVPlayer 本來就能同時出聲）。
    - WebKit 同一時間只讓一個有聲音的網頁媒體播放（R128 的實測：網頁格子同一時間只有一格有聲音）：小視窗的影片開始有聲音播放時，有聲音的網頁格子（YouTube 內嵌、網頁）會被 WebKit 暫停；App 本來就會把播放中的格子暫停並記下，關掉小視窗時一起恢復。
    - 如果 WebKit 播放時讓 App 收到 `AVAudioSession.interruptionNotification`（`.began`），在這裡看的期間不當作被其他 App 打斷：當作網頁開始播放（記下暫停的格子，關掉小視窗時恢復），不走 R128 的「全部暫停、結束時依系統決定恢復」。這段期間真的有來電時，也是關掉小視窗才恢復。
    - 網頁影片的全螢幕（YouTube 手機版的全螢幕按鈕）不特別處理：WKWebView 會用系統的全螢幕播放器；方向仍然受 App 固定的方向限制。
- 驗收條件（同 Android 版 R162 的 AC1–AC6，iOS 的寫法）：
  - AC1：版型 `1` 與單格全螢幕時，有聲音的格子左上角沒有小喇叭；版型 `2` 時照常顯示。
  - AC2：iPhone 直向、版型 `1`，打開小視窗：上面影片（16:9，從動態島下面開始）、下面小視窗，影片不重新載入、繼續播放；工具列照常自動隱藏；關掉後影片回到占滿畫面；轉成橫向時小視窗在原本的位置。
  - AC3：單格全螢幕（橫向）中打開小視窗：轉成直向、上下排；關掉小視窗轉回橫向全螢幕；離開全螢幕回到原本的方向（分割畫面）。小視窗開著時進入全螢幕不轉向。
  - AC4：搜尋分頁切換成「在這裡看」後，點影片在小視窗裡播放，格子不變；上方的標題、分頁 3 秒後隱藏，點小把手再出現；「放進格子」把這部影片放進空格。重開 App 後保留選擇。
  - AC5：在這裡看的影片開始有聲音播放時，播放中的格子暫停；關掉小視窗（或切到其他分頁、改回放進格子）後那些格子恢復播放；按格子的播放時，小視窗的影片暫停。
  - AC6：在這裡看時「上一頁」按鈕（或從左邊緣滑動）回上一頁；沒有上一頁時不顯示按鈕。
  - AC7：推薦、留言、聊天室分頁的行為不變（點影片換掉連結的格子，影片頁不播放）。

## 8. 非功能需求

- **免費 Apple ID 的限制：** 用免費 Apple ID 在 SideStore 安裝時，App 每 7 天要重新簽章一次（SideStore 可以在 iPad 上自己完成，但要定期打開 SideStore）；同時最多 3 個自己簽的 App（SideStore 本身占 1 個）；每 7 天最多註冊 10 個 App 識別碼。所以 MultiView 只用 1 個識別碼，不做 App 延伸功能，也不使用免費帳號不能用的 iOS 功能（例如推播通知、iCloud）。
- **效能：** iPad 上 `2×2` 播 4 路 1080p 直播 30 分鐘不當掉、不凍結（和桌面版相同）；`3×3` 依 R120 的結果。開啟 App 到看到格子不超過 2 秒（Python、yt-dlp、廣告阻擋規則都在背景準備）。
- **App 大小：** IPA 預計 60–80MB（Python 約 30–40MB、yt-dlp 約 3MB、廣告阻擋規則約 2MB）。R122 驗證後記錄實際大小。
- **安全：** yt-dlp 的更新檔必須通過官方 `SHA2-256SUMS` 的雜湊值驗證（R136）。用網址開啟（R126）只接受 http(s) 網址，依 R2、R12 的規則判斷。解析得到的串流網址不寫進設定檔（和桌面版相同）。
- **GitHub Actions 的用量：** 公開的 repo 使用 macOS 機器不收費；私人 repo 的 macOS 機器用量是 Linux 的 10 倍，要注意免費額度（未決事項）。
- **測試：** MultiViewCore 的邏輯（網址判斷、版型、格位、設定與清單的讀寫、yt-dlp 結果判讀、更新的協調）寫成單元測試，網址判斷沿用桌面版 `tests/unit/` 的測試案例。畫面、播放、手勢在 iPad 上手動驗收，清單放在 `tests/manual/ios-app.md`。因為沒有 Mac，所有自動測試都在 GitHub Actions 上跑。
