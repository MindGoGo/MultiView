## 0. 給接手的工作階段（先讀這一節）

這份文件寫成可以獨立閱讀：新的工作階段不需要看之前的對話，讀完這一節就能開始。

**專案是什麼**：MultiView 是在一個畫面裡分割顯示多個直播與影片的播放器。目前有兩個版本：

| 版本 | 位置 | 狀態 |
|---|---|---|
| 桌面版（Windows，Electron + React） | `electron/`、`src/` | 0.8.3，規格 R1–R118 |
| iOS 版（SwiftUI） | `ios/` | 0.0.27，規格 R119–R144，已在 iPhone、iPad 實測 |
| Android 版（Kotlin + Jetpack Compose） | `android/` | 開發中，規格 R145–R159、R161–R163（R160 是桌面版在 `main` 用的） |

**開工前要讀的檔案**（依順序；不用全部讀完，需要時再查）：

1. 本文件。
2. [ios-app.md](ios-app.md) 的第 4 節（需求）與第 11 節（實測紀錄）：Android 版大部分功能照 iOS 版的最終行為做，第 11 節記錄了每個問題的原因與修正，避免重踩。
3. 要對照實作時，看 iOS 版對應的程式（第 9 節列出對照表）。

**工作方式**（使用者的習慣，沿用）：

- 使用者用繁體中文溝通，文件、註解、提交訊息都用繁體中文，需求編號寫在提交訊息最後，例如 `[R150]`。
- 開發環境是雲端的 Linux 容器，**連不到 YouTube**，也沒有實體手機；能做的是寫程式、跑單元測試、在 GitHub Actions 上編譯。實際行為由使用者在自己的裝置上測，回報結果後修改。
- 每做完一批功能就升一個版本號、推上分支，等 GitHub Actions 編譯通過後請使用者更新測試。實測結果寫回本規格第 11 節。
- 發佈新版：**自動**。升 `android/gradle.properties` 的 `multiview.versionName` 並推送，GitHub Actions 測試通過後發現這個版本還沒有發佈，就自己建立 `android-v<版本號>` 標籤與 Release、放上簽章的 APK（開發環境不能推送標籤，所以由 Actions 建立）。使用者不用做任何事，直接下載安裝。**Release 的說明文字讀 `android/release-notes.txt`，升版本號時要一起改**（0.0.14 漏改，說明沿用了 0.0.13 的文字）；已經發佈過的版本再推送不會更新說明，要到 GitHub 網頁的 Releases 編輯。也可以手動建立標籤（和 iOS 版的 `ios-v*` 相同）。
- **目前的進度（2026-11-17）**：0.0.22 加入 R163（上下排時小視窗可以往上拉成占滿畫面、點影片只出現一列的操作列；`tests/manual/android-app.md` 的 M 組），**待實測**。0.0.21 加入 R162（只有一格時不顯示小喇叭、直向單格時上面影片下面小視窗、小視窗裡直接看影片；`tests/manual/android-app.md` 的 L 組），使用者實測：在小視窗裡播放時格子自動暫停，正常。0.0.20 加入 SponsorBlock（R161，跳過業配；`tests/manual/android-app.md` 的 K 組），**待實測**。之前：Android 版做到 0.0.19，第 10 節的步驟 1–7 都做了第一版，使用者在 POCO F6 Pro 上測過（結果在第 11 節）。0.0.14 加入其他網站用 yt-dlp 播放（R156 的「其他網站的播放方式」），使用者實測正常。0.0.16 加入字幕（yt-dlp 播放）與進度條的預覽縮圖；字幕讀得到，但顯示有兩個問題，0.0.17 修正，**待實測**（I 組）。0.0.15 加入語音選單（R156）與「用行動數據時不自動更新 yt-dlp」，使用者實測成功（H 組）。手動驗收步驟在 `tests/manual/android-app.md`。發佈是自動的：升 `android/gradle.properties` 的版本號並推送即可。
- **分支：`Phone`**（2026-11-15 起，Android 版與 iOS 版一起在這個分支開發）。開新的工作階段時，開發環境會指定一個新的 `claude/…` 分支：先從 `Phone` 開始（`git checkout -b <指定的分支> origin/Phone`），做完後合併回 `Phone` 並推送 `Phone`（使用者同意的做法；Actions 只在 `Phone` 上跑，所以要推到 `Phone` 才會編譯、發佈）。同一個提交不要同時推到好幾個分支。以前的分支（`claude/beautiful-babbage-1bur72`、`claude/pensive-tesla-rfgdz1`、`claude/focused-cerf-ovpv5r`、`claude/kind-darwin-fm9hki`）的內容都已經在 `Phone` 裡；使用者說先不要合併到 `main`。

## 1. 背景與目標

使用者想在 Android 手機與平板上使用 MultiView，功能和 iOS 版相同：分割畫面同時看多場直播與影片、各格獨立的聲音、yt-dlp 播放（沒有 YouTube 的廣告，而且原生播放器可以多格同時出聲）、網頁來源與廣告阻擋、清單、訂閱、YouTube 小視窗。

和 iOS 版相比，Android 版有幾個有利的地方：

- **安裝簡單**：直接安裝 APK，不需要 SideStore、不用每 7 天重新簽章、不用 Apple ID。
- **編譯不需要 macOS**：GitHub Actions 的 Linux 機器就能編譯（比 macOS 機器便宜、排隊短）。
- **分享選單**：App 可以直接出現在其他 App 的分享選單（iOS 版要使用者自己做捷徑）。

需要重新做的地方：程式語言不同（Kotlin），iOS 版的 Swift 程式不能直接用；Android 的 WebView 沒有 iOS 那種內容阻擋規則；Python 與 JS 執行環境的做法不同。

## 2. 範圍

**包含**：iOS 版第一版的全部功能（R119–R144 中已經實作的部分），在 Android 上的對應做法見第 4 節。

**不包含（之後再評估）**：

- 上架 Google Play（yt-dlp、YouTube 廣告阻擋很可能不能過審核；先用 APK 自行安裝）
- Chromecast（對應 iOS 版的 AirPlay，之後再評估）
- 音量、亮度超過 100%（和 iOS 版相同）
- YouTube 內嵌播放器的字幕選單（桌面版 R31；Android 版只做 yt-dlp 播放的字幕，R156）、接實體鍵盤的快捷鍵、多視窗（iOS 版也還沒做）
- Android TV

## 3. 共用定義

沿用桌面版與 iOS 版的定義（[multiview-player](multiview-player.md) 第 3 節、[ios-app](ios-app.md) 第 3 節）。另外：

- **原生播放器**：AndroidX Media3 的 ExoPlayer，播 mp4、m3u8 和 yt-dlp 解析出來的串流。對應 iOS 版的 AVPlayer。
- **網頁格子**：用 Android WebView 顯示的格子（YouTube 內嵌播放器、網頁來源、整頁模式）。
- **大螢幕／小螢幕**：寬度和高度都至少 600dp 是大螢幕（平板、摺疊機展開），其他是小螢幕（和 iOS 版的 600pt 相同）。

## 4. 需求清單

每一條都註明對應的 iOS 版需求；沒有特別說明的行為和 iOS 版相同。

### 第一階段：建置與技術驗證

### R145：建置與安裝流程（對應 R119）
- 描述：
  - 程式放在 `android/`，用 Gradle（Kotlin DSL）建置；畫面用 Jetpack Compose；最低支援 Android 8.0（API 26），目標版本 Android 16（API 36）。套件名稱 `local.multiview.android`（debug 版加 `.debug`，可以和正式版同時安裝）。
  - 版本號寫在 `android/gradle.properties` 的 `multiview.versionName`；versionCode 由版本號算出來（`主×1000000 + 次×1000 + 修`），版本號變大 versionCode 就變大。
  - 和畫面無關的邏輯放在獨立的 Kotlin 模組 `android/core/`（純 Kotlin，不依賴 Android），有自己的單元測試，可以在開發環境的 Linux 上直接跑（`./gradlew :core:test`）。開發環境沒有 Android SDK、也連不到 Google 的 Maven，所以找不到 Android SDK 時 Gradle 只載入 `:core`（不載入 Android Gradle Plugin），App 的編譯只在 GitHub Actions 上做。
  - GitHub Actions（`.github/workflows/android.yml`，Ubuntu）：**只在 `Phone` 分支觸發**（2026-11-15 起；iOS 的 `ios.yml` 也一樣），工作階段的 `claude/…` 分支不觸發，要的話在 Actions 頁面手動執行（Run workflow）。`Phone` 上改到 `android/` 或共用檔案（`electron/webPreload.ts`、`src/lib/**`、`resources/easylist.txt`、`ios/MultiView/YtDlp/mv_bridge.py`、`ios/scripts/easylist-to-webkit.mjs`）時跑單元測試並編譯 debug 版（APK 放在 Actions 的 Artifacts）；**自動發佈**：測試通過後，如果 `multiview.versionName` 的版本還沒有附 APK 的 `android-v<版本號>` Release，就自動建立標籤（指向這次的提交）與 Release，產生簽章的 APK（`MultiView-Android-<版本號>.apk`），用 `apksigner` 確認簽章後放上去，不標成最新版本；版本號沒變的推送不發佈。手動推送 `android-v*` 標籤也會發佈，但標籤和 `multiview.versionName` 要一致。
  - **簽章**：Android 的 APK 一定要簽章，而且更新時簽章要相同，否則不能覆蓋安裝。簽章金鑰存在 GitHub 的 Secrets（使用者建立，見第 12 節），不放進 repo。
  - **更新**：使用者可以用 Obtainium 之類的 App 追蹤 GitHub Releases 自動提示更新（對應 iOS 版的 SideStore 來源），或直接下載 APK 安裝。
- 驗收條件：
  - AC1：推送改到 `android/` 的提交 → Actions 的測試與編譯成功。
  - AC2：推送版本號 0.0.1 → Actions 自動建立 `android-v0.0.1` 的 Release 並附上 APK，可以在手機上安裝、開啟。
  - AC3：版本號升到 0.0.2 並推送 → 自動發佈；安裝後覆蓋安裝，資料保留。
  - AC4：推送沒有改版本號的提交 → 只測試與編譯，不發佈。

### R146：技術驗證：多格原生播放（對應 R120）
- 描述：技術驗證版（0.0.2）打開是測試畫面，可以切換「原生播放器」「YouTube 內嵌」與 `2×2`、`3×3`，每格有靜音與音量滑桿，網址可以自己換（一行一個）。4 格 ExoPlayer 同時播放、同時出聲。Android 的音訊焦點（audio focus）預設會讓一個播放器出聲時其他的暫停，所以每個 ExoPlayer 都要設定成**不處理音訊焦點**（`setAudioAttributes(…, handleAudioFocus = false)`），改由 App 自己處理來電等中斷（R153）。記錄 `2×2`、`3×3` 的效能（使用者的裝置）。
- 驗收條件：
  - AC1：4 格 m3u8 同時播放 10 分鐘，4 格都有聲音。
  - AC2：第 11 節記錄效能結果。

### R147：技術驗證：多格網頁播放（對應 R121）
- 描述：多個 WebView 同時放 YouTube 內嵌播放器，確認能不能同時出聲。iOS 的 WKWebView 同一時間只能一格網頁出聲（第二格出聲時系統暫停第一格）；**Android 可能沒有這個限制，要實測**。結果決定 R153 的網頁聲音規則。
  - 內嵌播放器需要 http(s) 的頁面來源：用 `loadDataWithBaseURL("https://local.multiview.android/", …)`（iOS 版用 `https://local.multiview.ios`）。
  - 要設定 `mediaPlaybackRequiresUserGesture = false` 才能自動播放。
- 驗收條件：
  - AC1：4 格 YouTube 內嵌播放器同時播放。
  - AC2：第 11 節記錄能不能同時出聲。

### R148：技術驗證：內嵌 Python 與 yt-dlp（對應 R122）
- 描述：
  - 用 **Chaquopy**（Gradle 外掛，開源）把 Python 3.13 和 yt-dlp、yt-dlp-ejs、certifi 包進 App。版本和 iOS 版相同（`ios/scripts/fetch-python.sh` 裡固定的版本）。
  - **直接重用 iOS 版的 `ios/MultiView/YtDlp/mv_bridge.py`**（解析、頻道影片列表、更新用的版本資訊），只把 JS 執行的部分換掉。
  - yt-dlp 解析 YouTube 需要 JS 執行環境。iOS 版寫了一個 yt-dlp 外掛（`ios/MultiView/YtDlp/mv_jsc.py`）把 JS 交給 JavaScriptCore。Android 有兩個選項，技術驗證時兩個都試：
    0. **（0.0.4 先試）AndroidX JavaScriptEngine**：`androidx.javascriptengine` 用手機 WebView 的 V8 執行 JS，在獨立的沙箱程序裡，不需要主執行緒也不需要顯示的 WebView；`mv_android.py` 把它包成 `mv_bridge.install_python_eval` 要的函式，`mv_bridge.py`、`mv_jsc.py` 不用改。不行再試下面兩個。
    1. **QuickJS**：yt-dlp 本身就支援（`--js-runtimes quickjs`）。把編譯好的 Android 版 QuickJS 執行檔放在 App 的 native library 資料夾（Android 允許執行 `nativeLibraryDir` 裡的檔案），告訴 yt-dlp 它的路徑。不用寫外掛。
    2. **WebView 的 JS**：照 iOS 版的 `mv_jsc.py` 寫一個外掛，把 JS 交給一個不顯示的 WebView 執行（`evaluateJavascript`）。WebView 要在主執行緒操作，要注意不要卡住畫面。
  - 解析要在背景執行緒；Python 同一時間只能跑一段程式（GIL），同時最多解析 2 個（和 iOS 版相同）。
- 驗收條件：
  - AC1：貼上 YouTube 直播 → 用 yt-dlp 解析，原生播放器開始播放。
  - AC2：第 11 節記錄用哪一種 JS 執行環境、解析時間、APK 大小。

### 第二階段：核心功能

以下照 iOS 版的最終行為（含第 11 節的修正）實作。

### R149：主畫面、版型、分隔線與換位（對應 R123–R125）
- 描述：
  - 只有影片格子，影片畫到螢幕邊緣（隱藏狀態列與導覽列，沉浸模式）；操作列、按鈕、輸入框避開瀏海與手勢導覽列的範圍。**注意**：iOS 版曾經在「已經忽略安全區域」的地方量安全區域，量到 0，結果下方的按鈕落在系統手勢範圍裡按不到（iOS 0.0.16）。Android 要用 `WindowInsets`（`systemBars`、`displayCutout`）在根畫面量，再傳給格子。
  - 版型：大螢幕 `1`、`2`、`2×2`、`3×3`、`1+3`；小螢幕只有 `1`、`2`，`2` 在畫面比較高時上下排列。版型按鈕是依格子位置畫的圖示。
  - 分隔線看起來 2dp、手指可以按的範圍 24dp；雙擊回到平均分配。格子之間有間隔，貼著螢幕邊緣的那一側沒有（不要有外框線，iOS 0.0.2 的問題）。
  - 換位：長按影片約 0.5 秒（或操作列的「移動」）後拖到另一格放開。
  - 播放中不自動關螢幕（`FLAG_KEEP_SCREEN_ON`）。
  - 旋轉按鈕：關了自動旋轉也能切換橫向、直向（`requestedOrientation`）。按一下轉成另一個方向並固定（按鈕變藍色），再按一下取消固定、回到跟著裝置旋轉（長按也可以取消）；手機直向時進入單格全螢幕自動轉橫向（方向被固定時也一樣），離開後回到原本的方向。
- 驗收條件：同 R123–R125，加上旋轉的 AC（iOS 0.0.26 的測試項目）。

### R150：加入來源（對應 R126）
- 描述：
  - 空白格：網址輸入框（有清除按鈕）、「貼上」按鈕。網址判斷和桌面版、iOS 版相同（共用測試案例）。點輸入框是開一個小視窗輸入（有清除、貼上），不直接在格子裡打字：鍵盤會蓋住下方的格子。
  - **分享選單**：App 在 `AndroidManifest.xml` 宣告接收 `ACTION_SEND`（`text/plain`），從其他 App 分享網址時出現在分享選單；從分享的文字裡找出第一個 http(s) 網址。也支援 `multiview://open?url=`（和 iOS 版相同，`ExternalLink` 的規則與測試照搬）。
  - 放進第一個顯示中的空格；沒有空格時詢問要取代哪一格。
  - 更換網址：小視窗，有清除、貼上。
- 驗收條件：
  - AC1：在 Chrome 或 YouTube App 按分享選 MultiView → 網址放進空格。
  - AC2：其他同 R126。

### R151：工具列與操作列（對應 R127）
- 描述：照 iOS 版的最終行為：
  - 點一下影片 → 只聽這一格，出現操作列與工具列；這一格的操作列顯示時再點一下就收起來；3 秒沒有操作自動收起；彈出的滑桿、選單開著時不自動收起（iOS 版曾經發生「⋯」選單被自動收起關掉，iOS 0.0.16）。
  - 工具列顯示時，每一格左上角有喇叭按鈕（只切換這一格的聲音），旁邊是「yt-dlp」小標示（不要蓋住喇叭，iOS 0.0.16 的問題）。
  - 操作列：播放／暫停、喇叭、音量、亮度、畫質、移動、全螢幕、子母畫面、網頁的「顯示整個網頁」與廣告阻擋、最愛、更換網址、移除；放不下的收進「⋯」選單（用系統的彈出選單，使用者覺得比底部對話框好看）。
  - 播放中點一下時中央顯示暫停鈕，暫停時一直顯示播放鈕。
  - 讀取動畫：彈跳的小生物（桌面版 R99 的圖案，iOS 版 `ios/MultiView/Cell/LoadingCritter.swift` 用程式畫的，座標可以照抄）。
  - 整頁模式的網頁格子：手指直接操作網頁，用格子下緣的小把手叫出操作列。
- 驗收條件：同 R127，加上 iOS 0.0.13、0.0.26 的測試項目。

### R152：聲音（對應 R128）
- 描述：
  - 點一下格子 → 獨占聲音；喇叭按鈕 → 只切換這一格；每格音量 0–100%。
  - 原生播放器（ExoPlayer）的格子可以多格同時出聲（R146 實測）。

    - 串流播放失敗：還沒開始播放過的，2 秒後用同一個串流再試一次（桌面版實測 Dailymotion 剛解析出來的網址前幾秒會被拒）；播放過的（例如串流網址過期）重新解析、從原本的位置繼續，最多 3 次。都不行就改顯示網頁。

    - 和桌面版的差別：沒有「改用網頁」按鈕（iOS 版也沒有；要用網頁就把設定改回「網頁」）。
  - **字幕**（0.0.16，待實測）：yt-dlp 播放時，`mv_bridge.py` 多回傳 `captions`（人工字幕，加上自動產生的原本語言，也就是 yt-dlp 的 `語言-orig`；自動翻譯的不列；只取 WebVTT）。有字幕時操作列有「字幕」（窄的在「⋯」裡）：「關閉」和各語言，自動產生的標「（自動產生）」。字幕檔由 App 自己下載、解析（`android/core` 的 `CaptionRules.parseVtt`，去掉每個字的時間標籤、YouTube 自動字幕捲動重複的那一行），疊在影片下方顯示（字幕的文字框固定占滿影片範圍，換文字時不重新排版），字的大小是格子高度的 5% 與寬度的 4.5% 取小的，左右留 5% 讓長句換行；讀不到字幕不影響播放。選的字幕存在來源的 `captions`（格式和桌面版 R31 相同：語言代碼，自動產生的前面加 `asr:`），重新開啟或換影片時依 R31 的規則找同一種語言。內嵌播放器沒有字幕選單。
  - **語音（聲音軌）**（桌面版 R95；0.0.15，實測成功）：yt-dlp 播放的 HLS 有兩條以上的聲音軌時，操作列有「語音」（窄的在「⋯」裡），列出語言與種類（原本的聲音、AI 配音、配音）。選擇的順序：這一格記住的語言 → 手機的語言 → 原本的聲音 → 第一條；選過的語言存在來源的 `audioLang`（和桌面版相同）。規則與測試照搬桌面版 `src/lib/audioTracks.ts`（`android/core` 的 `AudioTrackRules`）。
  - **2026-11 YouTube 的改動**（0.0.18）：YouTube 的測試讓 yt-dlp 的 `web_embedded` 用戶端拿串流時要 PO token，沒有就 HTTP 403；yt-dlp 2026.10.26 會用到它，使用者回報手機與桌面版的 yt-dlp 都播不了（2026-11-15）。yt-dlp 11/14 在 nightly 修正（issue #17989），還沒有正式版。`mv_bridge.py`（Android、iOS 共用）與桌面版 `electron/ytdlp.ts` 解析時加上 `youtube:player_client=default,-web_embedded`；之後的正式版也把這個用戶端排到後面，留著不影響。
  - **更新來源**（0.0.19，2026-11-15 使用者要求）：設定畫面的 yt-dlp 可以選「正式版」（`yt-dlp/yt-dlp`，預設）或「最新版」（`yt-dlp/yt-dlp-nightly-builds`，每天建置；檔案名稱與 `SHA2-256SUMS` 相同）。存在 App 的偏好設定（不是設定檔）。切換後馬上檢查並下載，重新開啟 App 後生效。最新版只往新的更新；正式版在比較新、或目前用的是最新版的版本（版本號有第四段）時下載（`YtDlpUpdateRules.shouldDownload`）。設定畫面顯示目前使用的版本。
  - 自動更新：每 24 小時檢查一次 GitHub 上 yt-dlp 的最新穩定版，下載 `yt-dlp`（zip 格式的 Python 程式）並用官方的 `SHA2-256SUMS` 驗證，存在 App 資料夾，**下次開啟 App 生效**；App 版本換了時刪掉下載的那一份。下載的那一份載入失敗時改用內附的。解析失敗、看起來是 yt-dlp 太舊時在背景更新（10 分鐘內一次）。用行動數據等計量網路時，自動更新不下載（對應 iOS 版的低數據模式；0.0.15）；設定畫面的「檢查更新」不受限制。這些規則和 `mv_bridge.py` 的 `use_update_archive`、iOS 版 `YtDlpUpdater.swift` 相同。
- 驗收條件：同 R135、R136。

### R157：網頁來源與廣告阻擋（對應 R137、R138）
- 描述：
  - **注入網頁的程式重用桌面版的 `electron/webPreload.ts`**，和 iOS 版相同的做法：寫一個 Android 版的 shim（對應 `ios/web/electron-shim.ts`）取代 `ipcRenderer`，訊息走 `addJavascriptInterface`（或 `WebMessageListener`），App 用 `evaluateJavascript("__multiViewReceive(…)")` 送狀態；用 esbuild 打包（`ios/scripts/build-web.sh` 的做法）。注意 Android WebView 的注入要在每個框架執行：用 AndroidX WebKit 的 `addDocumentStartJavaScript`（可以指定所有框架）。
  - 影片模式、整頁模式、找不到影片時按網站的播放鈕、15 秒後切整頁、YouTube 網站頁面點影片換成那部影片、其他網站用 yt-dlp：和 iOS 版相同。
  - **iOS 版踩過的坑（直接照最終做法）**：
    0. **Android 版的做法（0.0.10，待實測）**：寬版面用注入的程式把 `<meta name="viewport">` 改成 `width=1280`（WebView 設定 `useWideViewPort`、`loadWithOverviewMode`，整個網頁縮到剛好放進格子，只畫格子實際大小的畫面），找到影片後還原。WebView 不能把整個網頁靜音，所以注入的程式在每個框架定時把影片、聲音元素設成靜音。返回鍵：整頁模式的網頁回上一頁。
    1. 找影片時，網頁要用比較寬的版面排版（桌面版是至少 1280×720），否則手機上網站用窄版面，影片在畫面外找不到。但**不能把網頁畫成很大一張再縮小**（iOS 0.0.19 這樣做，記憶體不夠，網頁程序被系統結束）。iOS 版最後用網頁縮放（`pageZoom`，最小 50%）；Android 用 WebView 的 `setInitialScale`、`settings.useWideViewPort`／`loadWithOverviewMode` 或 `zoomBy` 做到同樣的效果，要實測。
    2. **寬版面只在找影片的期間使用**，找到影片後恢復原本的大小，否則注入的程式把影片設成「填滿畫面寬度」時，寬度是縮放後的寬度，影片只露出一半（iOS 0.0.22）。
    3. 找到影片前用黑色蓋住網頁，中間顯示讀取動畫（iOS 0.0.20）。
    4. **網頁開始顯示就算載入成功**（`onPageCommitVisible`），不要等「載入完成」：新聞網站一直在載入廣告，永遠等不到（iOS 0.0.21，news.tvbs.com.tw）。
    5. 載入成功過之後，網站自己的跳轉失敗不算錯誤；顯示錯誤後網頁又回報找到影片時，取消錯誤。
    6. 網頁程序被系統結束（`onRenderProcessGone`）時重新載入一次，還是不行才顯示「網頁停止運作」。
    7. 切換廣告阻擋而重新載入時，保留原本的顯示方式（不要回到影片模式）。
  - **廣告阻擋**：Android 的 WebView 沒有 iOS 的內容阻擋規則，要在 `shouldInterceptRequest` 裡比對每一個請求，擋下的回傳空的回應。
    - 規則來源：直接用 iOS 版的轉換結果（`ios/scripts/easylist-to-webkit.mjs` 產生的 JSON：`url-filter` 正規表示式、`if-domain`、`unless-domain`、`resource-type`、`load-type`、`ignore-previous-rules`）。這樣兩個平台擋的範圍一樣。
    - 比對要快：約 5 萬條網路規則，不能每個請求都跑 5 萬個正規表示式。做法：依規則網址裡的網域（`||網域^` 開頭的規則占大多數）建索引，請求只比對它的網域對得上的規則，加上少數沒有網域的規則。要寫單元測試與效能測試（`android/core`）。
    - 元素隱藏規則（`css-display-none`）：由注入的程式把對應網域的樣式加進網頁。
    - 其他網站裡內嵌的 YouTube 播放器（`youtube.com`、`youtube-nocookie.com` 的框架）發出的請求不擋（桌面版 R17 AC4）。
    - 設定畫面顯示規則數量。
- 驗收條件：同 R137、R138，加上 iOS 0.0.19–0.0.23 用 news.tvbs.com.tw 測的項目。

### R161：SponsorBlock（跳過業配等片段）
- 背景：[SponsorBlock](https://sponsor.ajay.app) 是群眾外包的資料庫，記錄 YouTube 影片中業配、開場、片尾等片段的起訖秒數，有公開 API、不需要金鑰。資料授權 CC BY-NC-SA 4.0，README 的第三方元件與設定畫面要註明來源。（R160 是桌面版在 `main` 分支用的編號。）
- **iOS 版照這一節做**：規則全部在 `android/core/.../SponsorBlock.kt`（純 Kotlin，不連網路、不碰畫面），測試在 `SponsorBlockTest.kt`；iOS 版在 `ios/MultiViewCore` 寫同樣的 `SponsorBlock.swift` 與測試（照搬案例，像字幕、語音選單、預覽縮圖那樣），App 端的做法見下面的「App 端」。
- 範圍：
  - **只處理 yt-dlp 播放的 YouTube 一般影片**（原生播放器）。
  - **不做**：YouTube 內嵌播放器、網頁格子與整頁模式、直播（含可回放的直播）、mp4／m3u8／其他網站、`mute`／`poi`（精華時間點）／`full`（整部都是業配）這幾種片段、送出或投票標記、片段的 `videoDuration` 和實際長度不同時的校正、跳過的次數統計。
- 描述：
  - **API**（隱私版）：`GET https://sponsor.ajay.app/api/skipSegments/<影片 ID 的 SHA-256 十六進位小寫的前 4 碼>?categories=[...]`（`categories` 是 JSON 陣列，網址編碼成 `%5B%22sponsor%22%2C…%5D`）。只送雜湊前綴，伺服器不知道在看哪一部。
    - 回應是陣列，裡面有很多部影片（前綴相同的），用 `videoID` 篩出目前這部；每部的 `segments` 有 `segment: [開始秒, 結束秒]`、`category`、`actionType`、`UUID`、`videoDuration`。
    - **404 代表沒有片段**，不是錯誤。
    - App 一律要**全部的類別**（下表 8 種），在本機依設定過濾：資料只有幾 KB，改設定時不用重新抓。
    - 逾時 5 秒（連線、讀取各 5 秒，等待也最多 5 秒）。失敗、逾時、格式不對都當作沒有片段，**絕對不能影響播放**（請求在背景，和 yt-dlp 解析同時開始；影片 ID 一開始就知道）。
    - **快取**：同一部影片在 App 執行期間只抓一次（記憶體快取，不寫檔）；好幾格同一部影片共用同一個請求。成功的結果（包含 404 的「沒有片段」）留在快取；失敗的不留，下次建立這部影片的播放器時再試（同一個播放器只試一次）。
    - **行動數據照常抓**（和 yt-dlp 自動更新不同，R156）：每部影片只有幾 KB。
    - User-Agent 用 `MultiView`。
  - **類別**（代碼、顯示名稱、進度條顏色；顏色和 SponsorBlock 官方擴充功能的預設相同）：

    | 代碼 | 名稱 | 顏色 |
    |---|---|---|
    | `sponsor` | 業配 | `#00D400` |
    | `selfpromo` | 自我宣傳 | `#FFFF00` |
    | `interaction` | 訂閱提醒 | `#CC00FF` |
    | `intro` | 開場 | `#00FFFF` |
    | `outro` | 片尾 | `#0202ED` |
    | `preview` | 預告與回顧 | `#008FD6` |
    | `filler` | 離題閒聊 | `#7300FF` |
    | `music_offtopic` | 音樂影片的非音樂部分 | `#FF9900` |

    `poi_highlight`（精華時間點，`actionType = poi`）不是要跳過的片段，第一版不列出。
  - **解析**（`SponsorBlockRules.parse`）：只取 `videoID` 相同的影片；只要 `actionType = skip` 的片段（沒有這個欄位也當作 skip）；`segment` 不是兩個數字、結束不大於開始、類別不認得的忽略；開始小於 0 時改成 0。`UUID` 是片段的 id（沒有時用「類別@開始秒」）。
  - **過濾與合併**（`SponsorBlockRules.select`）：關閉或一個類別都沒勾時是空的；只留勾選的類別；**短於 1 秒的忽略**；依開始時間排序；重疊或相接（下一段的開始 ≤ 這一段的結束）的合併成一段，類別與 id 用最早開始的那一段。
  - **自動跳過**（`SponsorBlockRules.check`，每 250 毫秒檢查一次，和字幕一樣用定時檢查播放位置的做法）：
    - 播放位置進入**還沒處理過**的片段（開始 ≤ 位置 < 結束 − 0.3 秒）時，跳到片段結尾；離結尾不到 0.3 秒時不跳。
    - **片段結尾在影片最後 1 秒內**（或超過影片長度）時，跳到影片長度，視為播完。不知道影片長度時跳到片段結尾。
    - 只在要播放（`playWhenReady`）而且是播放中或緩衝中時檢查；暫停時不跳。直播不檢查。
    - 跳過的片段標成「處理過」（`SkipState.markHandled`），**使用者倒回去看就不再跳**。
    - **使用者自己跳轉**（拖曳或點進度條、雙擊快轉倒轉，也就是 `CellPlayer.seekTo`）時，落點所在的片段標成處理過（`SkipState.userSeeked`），不會馬上又被跳走；落點在片段前面、之後播放進入片段時照樣跳。自動跳過本身不經過 `seekTo`，不會被當成使用者跳轉。
    - **從上次的觀看進度開始**（R55）：片段來了之後，上次的位置所在的片段當作使用者自己跳進去的，不跳（使用者上次就停在那裡）。
    - 跳過的狀態每一格各自保存（**多格互不影響**）；只存在記憶體裡，播放器重新建立（重新解析、換播放方式）後重新開始。
  - **跳過提示**：格子右上角顯示「已跳過<類別名稱>」（例如「已跳過業配」），左邊有類別顏色的小圓點，右邊是「取消」；5 秒後自動收起。按「取消」跳回片段開頭，這個片段之後不再跳（已經標成處理過）。工具列顯示而且格子在最上面一列時往下移，避開工具列。
  - **進度條**：一般影片的進度條上用類別的顏色畫出片段的位置（`SponsorBlockRules.marks` 算出 0–1 的比例；超過影片長度的部分截掉；最窄 2dp），畫在已播放的部分上面。拖曳進度條時，手指在片段上的話預覽提示多一行「<顏色> <類別名稱>」（`SponsorBlockRules.segmentAt`）。
  - **背景播放**（R154）：在背景只播聲音、透過 `PlaybackService` 播放時也照樣跳過（檢查用主執行緒的 Handler，App 在背景時照常執行）。
  - **設定**（設定畫面的「SponsorBlock（跳過業配）」）：
    - 「自動跳過片段」開關，**預設開啟**。
    - 開啟時列出 8 個類別的勾選框（左邊是進度條的顏色），**預設只勾「業配」**。
    - 改設定馬上套用到每一格（不用重新載入；關閉時色塊與提示消失）。關閉後再開啟時，還沒抓過的影片才去抓。
    - 說明：只處理 yt-dlp 播放的一般影片、每部影片只要一次資料（幾 KB，行動數據也照常）、只送雜湊前綴；資料來源與授權。
    - 保存在設定檔的 `sponsorBlock` 欄位：`{"enabled": true, "categories": ["sponsor"]}`（類別依上表的順序）。沒有這個欄位（舊的設定檔、桌面版的設定檔）時用預設值；`enabled` 不是布林值時用預設值；不認得的類別忽略；空的陣列保留（全部取消勾選）。
  - **App 端**（Android；iOS 版對照）：
    - `player/SponsorBlockClient.kt`：請求、快取（iOS：`SponsorBlockClient.swift`，`URLSession`）。
    - `player/YouTubeSourcePlayer.kt`：建立時就在背景抓片段（開啟、一般影片的播放方式是 yt-dlp 時）；yt-dlp 解析出來是一般影片時把片段與設定交給原生播放器，是直播時不處理。
    - `player/NativePlayer.kt`：過濾、定時檢查、跳過、提示、取消（iOS：`NativePlayer.swift` 用 `addPeriodicTimeObserver`）。
    - `ui/CellView.kt`：跳過提示；`ui/ControlsBar.kt`：進度條的色塊；`ui/ProgressPreview.kt`：預覽提示裡的類別；`ui/SettingsScreen.kt`：設定。
- 驗收條件：
  - AC1：用 yt-dlp 播一部有業配標記的 YouTube 影片，播到業配開始時自動跳到業配結束，右上角顯示「已跳過業配　取消」，5 秒後消失。
  - AC2：按「取消」跳回業配開頭，繼續播放業配，不再被跳過；倒回去重看已經跳過的業配也不再跳。
  - AC3：拖曳進度條到業配中間，從那裡繼續播放，不會被跳走；拖到業配前面，播放進入業配時照樣跳過。
  - AC4：進度條上業配的位置有綠色色塊；拖曳進度條經過業配時，預覽提示顯示「業配」。
  - AC5：設定關閉 SponsorBlock 後，色塊消失、不再跳過；勾選「開場」等其他類別後，那些片段也有色塊、也會跳過；設定在重開 App 後保留。
  - AC6：App 在背景只播聲音（或鎖定螢幕）時，播到業配也會跳過。
  - AC7：兩格各播一部（或同一部）有業配的影片，各自跳過、各自的提示與取消互不影響。

### R162：只有一格時的顯示、上下排的小視窗、在小視窗裡看影片（只有 Android 版）
- 背景：使用者要求（2026-11-17），先做 Android 版。桌面版不變。iOS 版 0.0.36 照搬（做法與差異見 [ios-app.md](ios-app.md) 的 R162）。
- 描述：
  - **小喇叭**：版型 `1`、單格全螢幕時，格子左上角不顯示「有聲音」的小喇叭（R7 AC5 的例外：畫面上只有一格，看得到也聽得到）。工具列顯示時左上角的靜音按鈕照常顯示。
  - **上下排**：手機（小螢幕）直向、畫面上只有一格（版型 `1`，或單格全螢幕）時打開 YouTube 小視窗：影片在上面，占滿寬度、16:9（從狀態列下面開始）；小視窗接在影片下面，占剩下的高度。格子是同一個畫面，不重新載入。轉成橫向時小視窗回到原本的位置（蓋在右側／占滿寬度）。上下排時工具列照常自動隱藏（小視窗沒有蓋住影片）。
  - **全螢幕中打開小視窗**：手機單格全螢幕（橫向）中按工具列的「YouTube 小視窗」：轉成直向並上下排；關掉小視窗（按鈕、返回鍵、打開清單）時轉回橫向的全螢幕。離開全螢幕時回到原本的方向（旋轉按鈕固定的方向，或跟著裝置）。小視窗開著時進入全螢幕不轉成橫向。
  - **在小視窗裡看**：搜尋分頁上方多一個圖示按鈕，切換「點影片」的方式：
    - 格子圖示（預設）：放進格子（原本的做法）。
    - 播放圖示（藍色）：在小視窗裡直接看，網頁照常換頁、播放；切換時上方提示目前的方式。選擇保存在 App 的偏好設定（不寫進和桌面版共用格式的設定檔）。
    - 在這裡看時：上方的標題與分頁和格子的工具列一樣，3 秒沒有操作就自動隱藏，點小視窗上方的小把手再叫出來；App 的工具列也照常自動隱藏。上方多「上一頁」（網頁有上一頁時）與「放進格子」（正在看的是一部影片時；放進空格，沒有空格時詢問要取代哪一格）。返回鍵先讓網頁回上一頁。
    - 聲音：網頁開始播放有聲音的影片時（搜尋結果裡靜音的預覽不算），正在播放的格子暫停（一次只聽一個）；關掉小視窗、切到其他分頁、改回「放進格子」時，網頁裡的影片暫停，因此暫停的格子恢復播放。這時按格子的播放，網頁裡的影片暫停。WebView 自己要音訊焦點造成的焦點遺失不當作被其他 App 打斷。
    - 不做：網頁影片的全螢幕按鈕（WebView 的 `onShowCustomView`）、網頁裡的廣告阻擋（和原本的小視窗相同，只有格子擋廣告）、推薦／留言／聊天室分頁的「在這裡看」。
- 驗收條件：
  - AC1：版型 `1` 與單格全螢幕時，有聲音的格子左上角沒有小喇叭；版型 `2` 時照常顯示。
  - AC2：手機直向、版型 `1`，打開小視窗：上面影片、下面小視窗，影片不重新載入；關掉後影片回到占滿畫面；轉成橫向時小視窗在原本的位置。
  - AC3：單格全螢幕中打開小視窗：轉成直向、上下排；關掉小視窗轉回橫向全螢幕；離開全螢幕回到分割畫面。
  - AC4：搜尋分頁切換成「在這裡看」後，點影片在小視窗裡播放，格子不變；上方的標題、分頁幾秒後隱藏，點小把手再出現；「放進格子」把這部影片放進空格。重開 App 後保留選擇。
  - AC5：在這裡看的影片開始播放時，播放中的格子暫停；關掉小視窗後那些格子恢復播放。
  - AC6：在這裡看時返回鍵先回上一頁，沒有上一頁時關掉小視窗。

### R163：上下排的小視窗與操作列的調整（Android、iOS 共用編號）
- 背景：使用者實測 R162（Android 0.0.21、iOS 0.0.36，2026-11-17）：在小視窗裡播放時格子會自動暫停，正常。介面要調整三處。
- 描述：
  - **拉成全螢幕**：上下排時，小視窗上方一直有一條小把手（標題列隱藏時就是原本那條叫出標題列的小把手）。
    - 按著小把手往上拉，小視窗跟著手指移動；放開時往上移動超過 40dp 就占滿畫面（從狀態列下面開始，蓋住影片，影片照常播放）。
    - 占滿畫面時往下拉超過 40dp，就回到影片下面；移動不到 40dp 時回到原本的位置。
    - 標題列顯示時，點一下小把手也可以切換。標題列隱藏時，點一下是叫出標題列（R162）。
    - Android 的返回鍵：在這裡看的網頁先回上一頁，接著把占滿畫面的小視窗收回影片下面，最後才關掉小視窗。
    - 關掉小視窗時重設成接在影片下面。
  - **上下排時點影片**：只出現格子的操作列，不出現上方的工具列（工具列會蓋住大半部影片）；左上角的靜音按鈕與播放方式標示也跟著不出現。要用工具列時先關掉小視窗。再點一下影片收起操作列。
  - **精簡的操作列**：格子很矮時，操作列只排一列：播放、喇叭、進度條、全螢幕、「⋯」，其他按鈕都在「⋯」選單裡。
    - Android：格子高度小於 260dp 時。
    - iOS：上下排時。
  - **iOS 工具列**：AirPlay 按鈕移到「YouTube 小視窗」按鈕後面（只有 iOS 版有 AirPlay）。
- 驗收條件：
  - AC1：上下排時按著小把手往上拉，小視窗占滿畫面，影片的聲音繼續；往下拉回到影片下面；拉一點點就放開時回到原位。
  - AC2：上下排時點影片，只出現一列的操作列（播放、喇叭、進度條、全螢幕、⋯），上方沒有工具列；再點一下收起。
  - AC3：iOS 工具列的 AirPlay 在 YouTube 小視窗按鈕的右邊。
